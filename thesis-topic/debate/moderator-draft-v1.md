# 主持人整合草案 v1（第三回合審查用）

## 0. 兩回合後的共識與分歧
- 共識：
  1. 「軌跡」一主一從。主＝旅客自己的計畫軌跡（多站行程），答案決定性、由程式算出；從＝群體行為（人潮、停留），只用通過效度門檻的資料。
  2. 單位是「原子題」（一題只問一個目標）；分類規則只用題面看得到的線索；每類對應一個可執行的程式模板。
  3. 標準答案＝「相對於某個知識庫快照（kb_version）的程式計算結果」；真實題用 EQR／DSL 標註後由程式重算。
  4. 系統＝LLM 解析成 DSL → 符號執行器；基線含 closed-book、文本 RAG、ReAct、code agent、oracle-DSL 上界；計分含拒答（+1/0/−1）。
  5. 頻率門檻（Phase 0）決定類別去留；雙胞胎題（模板問法 vs 真實問法）量化 realism gap。
- 分歧：地區（A 臺灣；B、C 京都）。題型細節（班次是否獨立、停留／下一站／票券／季節是否成類）。

## 1. 主持人對地區的暫定判斷：臺灣（臺北都會區＋主要觀光線）為預設，京都為替代
理由（請針對這些逐點反駁或同意）：
1. 使用者原話「題目不一定需要從網路找，可以想」→ 真實題只用於頻率校準與真實子集（約 500–800 則原子題），不必是海量來源；京都在題目量上的優勢權重因此下降。
2. 群體層的真值效度：臺北捷運分時各站進出量（data.gov.tw 128506，官方全量計數、OGDL）優於京都的照片代理量或快適度マップ（預測值、授權未確認）。
3. 活動資料：觀光署「活動」（7778）有結構化起訖時間；京都祭典／點燈資料零散。
4. 授權：臺灣核心知識庫可整包釋出（OGDL＋ODbL）；京都的市巴士 GTFS 授權未確認、地下鐵 GTFS 查無、鐵道需手工區間層。
5. 時程風險：京都需要多個外部核准（ODPT 條款、NII 申請、Flickr Pro）；臺灣只需 TDX 註冊。
6. 研究生在臺灣，可實地核對、在地標註者容易找。
已知弱點：臺北捷運與多數市區公車是班距制（只能給區間）；觀光署營業時間是自由文字且含停業點位；繁中國旅提問的量在本環境無法查證（搜尋引擎幾乎不索引 PTT／Dcard）；臺灣旅客停留時間只能靠遊記。

## 2. 題型（7 類，臺灣預設版）
| 類 | 給定 → 問 → 答案型別 | 標準答案 | 例題 |
|---|---|---|---|
| Q1 指名對象時間狀態 | 1 個指名地點或活動（＋時刻/日期）→ 開不開、開放時段、幾點關、活動期間 → Bool／時間區間／日期區間 | opening_hours 規則＋辦公日曆；活動起訖 | 故宮下週一有開嗎？ |
| Q2 單程交通 | 起點＋1 個終點（或 1 站＋路線方向）（＋出發/抵達時刻）→ 下一班/首末班、幾點到、多久、最晚幾點出發、轉幾次、趕得上嗎 → 時刻／分鐘／整數／Bool | GTFS＋RAPTOR/OTP2＋OSM 步行；班距制給區間 | 明早 9 點從臺北車站出發，最快幾點到九份？ |
| Q3 行程檢核 | ≥2 個目的地且順序已給＋出發時刻（＋停留；未給則用群體層預設值）（＋截止）→ 可不可行、第 k 站幾點到、幾點結束、哪站先出問題 → Bool＋站／時刻 | 逐站前向模擬（Q1＋Q2 引擎） | 10 點從臺北車站出發，先中正紀念堂再國父紀念館各 1 小時，16 點前到得了 101 嗎？ |
| Q4 行程排序 | 2–5 個未排序目的地＋起點、出發時刻（＋停留、截止）→ 最佳順序、最多去幾個、能否全去 → 序列／整數／Bool | 窮舉 ≤120 種排列，以 Q3 模擬器評估；接受任一最佳解 | 下午 1 點出發，故宮、士林夜市、北投溫泉博物館怎麼排？ |
| Q5 條件式找地點 | 錨點（點、起訖路線、或候選集合）＋類別/候選＋約束（距離、步行或運輸時間、繞路上限、某時刻營業、某期間活動）→ 地點集合或最佳者（含「附近」「順路」「住哪裡方便」）→ 集合／單一地點 | 路網距離/等時圈＋過濾；住宿比較＝到各目的地總旅行時間，差 <5% 並列 | 西門站走路 10 分鐘內、晚上 9 點還開的博物館？ |
| Q6 時段人潮（相對） | 有官方計數的地點（捷運可達景點）＋日型＋候選時段 → 哪個時段人最多/最少、兩時段比較 → 時段／Bool | 近 N 週出站量分時平均；第一名在 ≥80% 週次維持才收題；附 n；只做相對比較 | 週六去淡水，哪個兩小時時段人最少？ |
| Q7 停留時長 | 1 個地點（＋日型）→ 一般待多久、X 小時夠不夠 → 時長區間（如 <1h、1–2h、2–4h、半天、一天）／Bool | 遊記抽取的停留分布（抽取器先用標註集驗證）；n ≥ 30；跨平台一致才收題 | 九份老街一般逛多久？半天夠嗎？ |

## 3. 依序決策規則（第一條成立就停）
- R0 原子化（多意圖拆開）；範圍外 → 排除清單。
- R1 問的是「別人／大家」的行為量？人多人少、擠不擠、哪時段人少 → Q6；單一地點一般待多久、X 小時夠不夠 → Q7。
- R2 題目給了旅客自己要去的 ≥2 個目的地（不含起點）？順序已給 → Q3；順序未給或問先後 → Q4。
- R3 答案是題目中「未指名」、要從類別或候選中找出／選出的地點？→ Q5。
- R4 只有 1 個目的地（或 1 條路線方向），問移動？→ Q2。
- R5 單一指名地點或活動的時間屬性？→ Q1。
- 其餘 → 未覆蓋；Phase 0 若 ≥5% 則新增類別。

邊界示例：「故宮幾點關」Q1 ／「4 點從臺北車站出發到故宮來得及參觀嗎」Q2（期限由 Q1 推得）；「九份半天夠嗎」Q7 ／「早上九份、下午十分，一天夠嗎」Q3；「先九份還是十分」Q4；「住臺北車站還是西門比較方便去九份和淡水」Q5。
KB 查不到真值的題（例如非捷運景點的時段人潮）→ 標為「不可答」，用於評估拒答。

## 4. 排除清單
即時資訊（誤點、即時人潮）；主觀評價／推薦；天氣、氣候、日出日落；票價與票券（列延伸）；自駕、停車；多日完整行程生成；無障礙、寵物等少見需求；跨意圖多跳題（如「照這樣排哪站會遇到人潮」）。

## 5. 「常見」的驗證（Phase 0，第 1 個月）
抽 ≥600 則真實提問（Dcard 旅遊、PTT 相關板、Mobile01 國內旅遊、背包客棧台灣、r/taiwan 每週旅遊串、WildChat 台灣旅遊子集）→ 原子化 → 兩人依 R0–R6 標註，κ ≥ 0.8（另報最易混淆的配對：Q2/Q3、Q1/Q2、Q4/Q5、Q6/Q7）。保留門檻：佔範圍內原子題 ≥3%、Wilson 95% 下界 ≥1.5%、出現在 ≥2 個平台。

## 6. 資料
- 知識：TDX（臺鐵、高鐵、公車 GTFS、捷運首末班與班距、觀光 POI/活動）；臺鐵時刻表 6138；臺北捷運 131735/131736/128506；觀光署 7777/7778/7779；辦公日曆 14718；OSM（Geofabrik，ODbL）；遊記（部落格、PTT/Dcard 遊記，只釋出 URL＋抽出序列）；（選用）觀光署遊憩據點月別遊客人數（data.gov.tw 7327 為「類型別」月統計；逐據點資料在觀光署統計資料庫，下載方式未確認，2026 年起統計口徑修訂）。
- 題目：自建模板＋程式解（主體，約 1 萬題）；人工驗證測試集（7 類×200）；真實子集 300–500 題（雙胞胎）；不可答子集。
- 工具：OTP2（LGPL）、opening_hours.js、PostGIS、DuckDB。

## 7. 系統與評估（同共識第 4 點）
解析器兩版：API LLM few-shot；7–8B 開源模型 LoRA。指標：各類答案正確率（EM/容差/集合 F1/最佳解差距/區間正確）、過程（DSL 槽位 F1、實體連結、時間正規化、軌跡有效率）、穩健（改寫一致、反事實日期）、拒答、realism gap（McNemar）、成本。

## 8. 京都替代方案（若最後選京都，改動處）
題目來源改 PTT Japan_Travel 等；交通改「市巴士 GTFS＋手工鐵道區間層＋步行」；Q6 改用快適度マップ（需確認授權）；Q7 用遊記（含 Arukikata、PTT 遊記）＋照片；可加「Q8 季節物候（JMA）」；票券列延伸。

## 9. 時程與關卡
M1 Phase 0＋資料可行性 → M2–4 知識庫與真值引擎 → M5–6 出題與人工驗證 → M7–9 系統與基線 → M10–11 實驗 → M12 撰寫。
關卡：營業時間可解析 <50% → 改 OSM＋人工 200 POI；Q6 可用觀光站 <15 → 降為延伸；Q7 抽取 F1 <0.9 或樣本不足 → 降為延伸（Q3 題目中明示停留時間）；任一類未達頻率門檻 → 併入相鄰類或刪除。
