## 立場 C 第二回合：交叉質詢與修正後的推薦
> ptt.cc 和 arxiv.org 仍然無法用 WebFetch 連線，以下抽查和補充樣本都改用 WebSearch。

### 1. 質詢

**對 A（臺灣結構化知識庫派）**

- **A1｜「程式算出的 gold」其實建立在文字抽取上。**
  - A 的 C1、C5、C6、C7 都要用到營業時間。依 A 自己的流程，觀光署的 ServiceTimeInfo 和 OpenTime 欄位要先用 LLM 轉成 opening_hours 語法。
  - [NYCU TDX 指南](https://bookdown.org/chiajungyeh/TDX_Guide/other-tdx-data.html)也提醒：觀光點位資料更新週期長，已停業的點位仍留在資料裡，部分縣市也沒有完整調查。
  - 那 A 的 C1 和 C 的「官方文字 → 正規化規則」有什麼本質差別？抽 300 筆人工核對，能涵蓋多少出題用的 POI？
  - 知識庫本身有錯時，gold 只是「正確地算出錯的答案」。知識庫準確率要怎麼反映在評分裡？

- **A2｜臺北深度區的精確題從哪裡來？**
  - 旅客在臺北主要搭捷運和公車。但 A 自己說捷運是班距制、只出區間題，精確題只出臺鐵和高鐵。這樣精確題多半是城際題，不是深度區的題。
  - A 用「例行題旅客會直接用地圖 App 解決」來批評論壇有偏差，但 A 的 C3「下一班幾點」、C4「最快幾點到」正好就是地圖 App 一鍵能答的題。
  - A 自己引用的 Ram/Gal-Tzur/Rechavi 2021 分析了 8,905 則都市大眾運輸提問。這反而說明論壇上的例行交通題數量很多。
  - [MetroLLM-Bench](https://arxiv.org/abs/2609.10016) 已經涵蓋臺北捷運：11 類（包含路線和票價）、955 個案例，4B 微調模型的 Tier-1 分數達 91.3。A 在臺北交通題上的新意還剩多少？
  - A 說 ChatPlanner 報告「GPT-5 加地圖工具的端到端可行率約 1/3」。我查到的[摘要](https://arxiv.org/abs/2606.15315)只寫 ChatPlanner 能可靠產生可行解，沒有這個數字。請提供出處。

- **A3｜分類軸不一致，而且缺少繁中真實題。**
  - C2 同時收「指名活動」和「區域＋日期搜尋活動」，但常設地點卻拆成 C1（指名）和 C5（搜尋），兩種對象用的是不同的分類軸。
  - C3 和 C4 以「需不需要選路」劃界。可是「新竹到臺北區間車要多久」這種問句，標註者只看得到文字，看不出需不需要選路。
  - 題目有 80% 是繁中，卻沒有任何已查證的繁中真實題來源：A 的 Q3（PTT、Dcard）標的是「未查證」。
  - 票價和天氣是事先就排除，而不是由資料決定要不要收。

**對 B（京都群體軌跡派）**

- **B1｜照片量能拿來當人潮的 gold 嗎？**
  - 攝影者常刻意避開人潮。我在補充檢索中看到，PTT 和背包客棧的回覆都建議清晨去伏見稻荷、清水寺拍「空景」。
  - 照片時間不可靠：B 自己的 pilot 就出現 1864 年的時間戳。
  - Flickr 的使用者群也不代表台灣旅客。
  - G3 的 r 值是「相對這個 POI 自己最忙時段」的比例，但旅客問的是絕對擁擠程度。
  - B 已經引用[京都観光快適度マップ](https://ja.kyoto.travel/comfort/)：它用 KDDI 位置資料加 Prophet，提供分時段預測，2023 年 10 月起也納入外國人資料。既然有這個，為什麼不直接用它當 gold？它和照片統計衝突時，以哪個為準？

- **B2｜資料量撐得起一個 benchmark 嗎？**
  - B 自己的 pilot 結果：
    - 大阪 27 個 POI 中，只有 11 個達到 30 人造訪。
    - 2 個錨點中，只有 1 個有明確的下一站。
    - 大阪城停留時間的 80% CI 是 20.7–53.9 分鐘，跨了兩個時長區間。
  - 2015 年以後的 Flickr API key 只開放給付費 Pro 帳號（[Flickr Help](https://www.flickrhelp.com/hc/en-us/articles/4404070036884-Flickr-API)）。
  - 如果 CI 很寬，「答案落在 CI 內就算對」的判分方式，會讓 closed-book 模型直接猜「一小時」也拿分。這樣還分得出系統的好壞嗎？

- **B3｜題型和真實問法對不上。**
  - 我的檢索沒有找到 2023 年以後「看完 X 接著去哪」的獨立提問。順路的建議都嵌在行程請益裡，而且是依地理遠近決定，不是看群體統計。
  - 「清水寺 vs 金閣寺」這類貼文問的是哪個值得去（偏好），不是 G6 的「哪個比較多人去」。
  - B 的 R0 把營業時間、怎麼搭車、時刻表都排除了，但 P1 又要用 OSM 營業時間和路網時間。B 排除的正是 P1 自己需要的元件。

### 2. 回應與承認

**補充樣本**
- **方法**：共 15 組 WebSearch，其中 12 組限定 ptt.cc、3 組限定 backpackers.com.tw。每組查詢是「[問題]」加上某一個子題型的關鍵詞。
- **計數規則**：只算標題明確屬於該子題型、且依 URL 時戳在 2023 年 1 月以後的不同文章。
- **限制**：每組只看前 10 筆，所以數字是「搜尋得到的下界」，不是比例。

| 子題型 | PTT 2023 年後的不同 [問題] 文 | 例子或備註 |
|---|---|---|
| 住宿區位 | 8 | [淺草 or 日暮里](https://www.ptt.cc/bbs/Japan_Travel/M.1762414108.A.C87.html) |
| 人潮、何時人少 | 6 | [如何避開京都週末的人潮](https://www.ptt.cc/bbs/Japan_Travel/M.1686989743.A.3B5.html)；背包客棧另有 4 串以上 |
| 行李寄放（周邊查找） | 5 | [心齋橋站附近寄放行李](https://www.ptt.cc/bbs/Japan_Travel/M.1682561322.A.226.html) |
| 機場、末班車 | 3 | [成田晚班機交通](https://www.ptt.cc/bbs/Japan_Travel/M.1720148006.A.518.html) |
| 營業時間（年末年始）、票券、物候、行程太趕 | 各 2 | 背包客棧另有 5 串以上票券串 |
| 停留時長 | 1 | [小樽排一整天會太多嗎](https://www.ptt.cc/bbs/Japan_Travel/M.1762928146.A.0B2.html) |
| 天氣、穿著 | 0 | 板方把這類詢問集中到每月的 [公告] 實況回報串（例：[113.11](https://www.ptt.cc/bbs/Japan_Travel/M.1730391034.A.74B.html)） |

**(1) 論壇選擇偏差：接受。**
- 論壇上的頻率不等於旅客的需求頻率。而且板規本身也會改變分布：天氣題被集中到每月的串，逐篇計數就會低估。
- 不過這是程度上的偏差，不是有沒有的問題。A 自己引用的 8,905 則提問和我找到的機場末班題都顯示，例行題仍然很常見。
- 修正做法：
  1. 多來源交叉比對：論壇文章、月串推文，再加上 WildChat（使用者向 LLM 的真實提問）。
  2. 頻率只用來決定某類收不收（門檻：占 5% 以上、出現在 2 個以上來源、跨 2 季以上）。評分一律用各類的 macro 平均，另外附上依論壇頻率加權的分數。

**(2) 關西鐵道時刻表：第一回合我低估了這個問題。**
- 京都市巴士有 GTFS（2024 年 1 月起公開）。京阪、阪急、近鐵、JR 西日本、京都市營地下鐵，都查不到開放的 GTFS。
- 修正做法：
  - 範圍收斂到京都市核心。
  - 精確答案只來自市巴士 GTFS 加 OSM 步行路網。
  - 鐵道部分：從官方時刻表手工整理約 8 條觀光路線的「站間所要時間」和「各時段班距」。只在內部使用，不散布。
  - 鐵道題一律給區間答案，做法和 A 處理臺北捷運一樣，用檢核器加區間涵蓋來評分，不出「幾點那一班」這種精確題。
  - 第 1 個月抽 50 段行程，和官方時刻表比對。至少 90% 落在區間內才算通過，沒通過就改做臺灣。

**其他承認**
- 我第一回合的 C7 氣候其實是查表，推理成分低，改成併入季節類。
- 我排除人潮是錯的，補充樣本顯示人潮題很常見。改成收錄，但 gold 用官方指數，不用照片。
- A 說「答案會過時、難擴充」。我的 gold 不是人工寫答案，而是人工標註 EQR（題目的可執行表示），再由程式算出答案。換一份知識快照就能重算，這和 A 的 kb_version 做法相同。

### 3. 指定議題

**(a) 地區**

| 項目 | 臺灣 | 京都 | 勝出 |
|---|---|---|---|
| 題目來源量 | 分散在 PTT 各地方板、Railway 板、ask 板和 Dcard；英文提問靠 r/taiwan 的每月問答串 | PTT Japan_Travel（索引頁超過 8,400 頁，另有每月串）、背包客棧關西版、Dcard 日本旅遊版 | 京都 |
| 時空知識 | TDX 有臺鐵、高鐵 GTFS，捷運只有班距；營業時間是自由文字，還混有已停業的點位 | 只有市巴士 GTFS，鐵道沒有開放資料；JMA 物候是京都獨有的優勢 | 交通：臺灣；季節：京都 |
| 群體軌跡 | 只有捷運分時 OD，分不出旅客和居民 | 快適度マップ、遊記、照片 | 京都 |
| 授權 | 政府資料開放授權（OGDL），可再散布 | JMA、祝日相容 CC BY；ODPT 和快適度マップ未查證；官網保留著作權 | 臺灣 |

- **表態：以京都市為核心。**
  - 這篇論文的獨特之處在「台灣旅客的真實提問加上可執行答案」，題目來源量決定能不能證明哪些題型常見。
  - 京都市內的觀光移動大量依賴市巴士：京都市[停售巴士一日券](https://trafficnews.jp/post/128380)，就是為了把觀光客分流到地鐵。而市巴士正好有精確的 GTFS。
- **第 1 個月的關卡**：以下任一條成立，就把同一套方法搬到臺灣做：
  - ODPT 條款不允許研究使用。
  - 鐵道區間層的驗證沒有通過。
  - 京都範圍內的原子題少於 600 題。

**(b) 「軌跡」的定位：一主一從。**
- 主：個人的計畫軌跡（T3 到 T5），答案是決定性的。
- 從：群體統計，只用在兩個地方。
  1. T4 題目沒給停留時間時，當預設值寫進題目情境，並附上樣本數 n 和來源。
  2. 延伸類 T8（人潮），附等級或區間，不併入主分數。
- 理由：群體統計沒有獨立的真值，資料量也不確定，B 自己的 pilot 已經證實這兩點。

**(c) 題型覆蓋**
- **該收**：
  - 營業與活動狀態
  - 起訖交通（含首末班、機場、票價）
  - 票券
  - 順路與行程可行性
  - 住宿區位
  - 物候和氣候（合併成一類）
  - 周邊查找（含行李寄放）
  - 人潮（放在延伸）
- **該排除**：
  - 獨立的「停留時長」類：獨立提問少，改當預設值使用。
  - 「看完接哪裡」和「人氣比較」：真實問法其實是順路或偏好。
  - 即時預報、停駛應變、主觀推薦、非時空題。
- A 排除票價和天氣、B 排除交通和營業時間，都和補充樣本的結果不符。

**(d) 邊界一致性**
- **A 的 C2 和 C1/C5**：應該統一成一條軸：「指名查詢」和「條件搜尋」。地點和活動都照這條軸分。
- **A 的 C3/C4**：改用問句上看得到的規則：
  - 問句固定了車種或某一班車，只問各站時刻 → C3。
  - 問 O 到 D 的抵達時刻、時長、趕不趕得上 → C4。
  - 更好的做法是兩類合併，用子型別標註，再實測標註一致性 κ。
- **B 的 G3**：效度低（理由見 B1），照片量只能當特徵，不能當 gold。
- **我的 C7 氣候**：不夠格獨立成類，併入 T6。
- **我的 C3 票券**：一半是時空題（各段行程是否在票券的區域和效期內），一半是算術（划不划算）。保留這一類，但「涵蓋」和「金額」分開計分。

**(e) 一人一年做得完嗎？**
- 三派的原案都做不完。
- **核心（第 1–10 個月）**：
  - T1 到 T7
  - 約 800 題真實原子題的測試集
  - 約 5,000 題模板訓練題：沿用 A 的生成器，加 round-trip 檢查
  - 系統與 baselines
- **延伸（第 10–12 個月，可以捨棄）**：
  - T8 人潮
  - 從遊記算停留時間的先驗
  - 臺灣遷移子集
- 進度落後時，T3 是第一個移到延伸的類別。

### 4. 最終推薦

- **題目**
  - 中：〈旅客怎麼問、答案怎麼算：以台灣旅客真實提問為本的京都時空與行程問答基準〉
  - 英：*Ask Like a Traveler, Answer Like a Program: A Real-Question-Grounded Spatio-Temporal and Itinerary QA Benchmark for Kyoto*
- **地區**：京都市核心。往返關西機場和大阪的題只出區間答案。
- **核心資料來源（8 個）**：
  1. PTT Japan_Travel（[問題] 文章和每月串）
  2. 背包客棧日本關西版
  3. WildChat-1M（ODC-BY 授權）
  4. 京都市巴士 GTFS（經 ODPT）
  5. 官方時刻表，自建鐵道區間層
  6. OSM 關西 extract（ODbL）
  7. JMA 物候觀測與平年值
  8. 內閣府祝日 CSV，加上官網營業時間與票券規則的快照（Wikivoyage 補充）
  - 延伸用：京都観光快適度マップ，確認授權後才使用。

**題型分類**

| 類別 | 定義（給定 → 問 → 答案型別） | Ground truth 怎麼算 | 例題 |
|---|---|---|---|
| T1 指名對象狀態 | 指名的地點或活動＋時刻或日期 → 有沒有開、開放時段、活動期間 → Bool＋時間區間 | 官網規則正規化成 opening_hours（雙人核對），加上祝日 CSV 和活動日程快照 | 1/1 早上伏見稻荷能參拜嗎？ |
| T2 單一起訖移動 | 起點 O、終點 D（＋時刻約束）→ 路線、時長、票價、首末班 → 路段、分鐘、日圓（巴士精確，鐵道給區間） | 在巴士 GTFS 上跑 RAPTOR，加上鐵道區間層和步行時間；接受 Pareto 最佳解 | 京都站搭巴士到銀閣寺要多久？ |
| T3 票券涵蓋與划算 | 各段行程與日期＋候選票券 → 有沒有涵蓋、划不划算、選哪張 → Bool 或最佳選項＋日圓 | 官方涵蓋規則，加上各段票價加總後比較 | 一天搭巴士跑金閣、銀閣、清水，買一日券划算嗎？ |
| T4 行程可行性與順序 | 時間窗、起點、至少 2 站、停留時間 → 排不排得完、最佳順序 → Bool＋時刻表或排列 | 用 T1 和 T2 的引擎模擬；6 站以內窮舉；任何經檢核器驗證可行的排程都算對 | 9 點出發，金閣、龍安、嵐山各待 90 分鐘，17 點前排得完嗎？ |
| T5 住宿據點選擇 | 至少 2 個候選區＋目的地集合 → 住哪裡最省時 → 最佳區＋各區總時間 | 平日 09:00 出發時，T2 旅行時間加總；差距小於 5% 視為並列 | 住京都站還是河原町比較省時？ |
| T6 季節與氣候 | 地點＋日期或月份＋現象或氣象量 → 何時發生、可見機率、數值 | JMA 物候平年值與逐年觀測（用固定的可見窗口規則）、月平年值、天文算法算日落時刻 | 4/8 京都還看得到櫻花嗎？ |
| T7 條件式周邊查找 | 錨點＋類別＋步行分鐘數（＋某時刻營業）→ 符合條件的 POI 集合 | 用 OSM 和官方清單逐項驗證約束；指標 valid@k | 京都站走路 5 分鐘內，哪裡能寄放大行李？ |
| T8 時段人潮（延伸） | 區域＋候選時段 → 哪個時段人少、擁擠等級 | 快適度マップ快照的時段等級 | 週六的嵐山，9 點和 14 點哪個人少？ |

**依序決策規則**（第一個成立就歸入該類）
- R0：不在範圍內、問的是偏好、或需要即時資料 → 不收
- R1：比較 2 個以上的住宿區 → T5
- R2：問票券 → T3
- R3：問擁擠程度或哪個時段人少（包含沿著行程問）→ T8
- R4：有 2 站以上，並問時間窗或順序 → T4
- R5：單一起訖 → T2
- R6：指名的地點或活動 → T1
- R7：自然現象或氣象量 → T6
- R8：沒指名地點，按類別和約束條件查找 → T7
- 都不符合 → 標為「未覆蓋」。若這類在 Phase 0 中占 5% 以上，就新增類別。

**排除清單**
- 即時資訊：誤點、即時人潮、天氣預報
- 停駛應變
- 主觀評價
- 入境、通訊、金流、訂位
- 多日完整行程生成
- 自駕與停車
- Phase 0 中占比不到 1% 的題型

**系統**
- 用 LLM 把問題解析成 DSL；另外訓練一個 LoRA 7B 版本，一般 GPU 就能跑。
- 中文和日文地名的實體連結。
- 執行器：RAPTOR 路徑搜尋、opening_hours 評估、票券計算、JMA 查表、OSM 空間索引。
- 知識庫查不到的事實，退回去檢索官網和 Wikivoyage。
- 答案附上 as-of 日期和引用來源；證據不足時拒答。

**Baselines**
- closed-book LLM
- 文本 RAG
- 直接呼叫原始工具的 ReAct 代理
- code agent
- 給正確 DSL 的上界（oracle-DSL）
- 論壇最高推文（代表群眾答案）

**指標**
- 各類別依答案型別用完全比對、容差、區間涵蓋、valid@k 或 QWK，總分取 macro 平均。
- 過程指標：DSL 槽位 F1、分類標註一致性 κ。
- 真實性落差：同一個 EQR 的「真實問法」和「模板問法」之間的準確率差，用 McNemar 檢定。
- 時效正確率：有沒有用到已失效的事實。
- 答對 +1、拒答 0、答錯 −1 的總分。
- 成本：token 數和延遲。
