# 立場 A 第二回合：交叉質詢與修正後的最終推薦

**查證說明**：本回合新增的事實都用 WebSearch 抽查過，因為 data.gov.tw 和 arxiv 都無法直連。B、C 的立論已經全文讀過。

## 1. 質詢

### 對 B（群體軌跡派）

**B-1：主資料集還不存在，答案也無法重現。**
- 主測試集靠的是 2015 年以後的 Flickr 照片，但 Flickr 官方說明頁寫明 API key 只發給付費的 Pro 訂閱者。ToS 又限制長期快取，所以第三方要重建 B 的答案，只能自己付費重抓，而照片可能早已刪除。
- B 自己的 pilot 顯示資料很薄：大阪 27 個 POI 只有 11 個達到 30 人；「下一站」問題能回答的錨點，2 個裡只有 1 個。
- 京都 2015 年以後的資料量，B 還沒算。資料不夠時的退路是「放寬門檻」，但這會直接削弱 B 賴以成立的「統計上可回答」。
- **追問**：京都 2015–2026 年間，至少有 30 個旅客日（user-day）的 POI 實際有幾個？

**B-2：用照片量代表人潮（G2、G3），沒有效度證據。**
- 照片量和遊客數的對應，文獻驗證過的都是年或月的尺度：
  - 836 個地點的研究顯示兩者呈冪律關係，指數約 0.7（[Wood et al.](https://www.nature.com/articles/srep02976)）。
  - 芬蘭與南非 56 個公園的月相關約 0.7，而且 Flickr 比 Instagram 弱（[整理](https://headwaterseconomics.org/?p=31338)）。
  - 小時尺度的驗證，本回合一篇都沒找到。
- G3 的擁擠等級是用「該地點自己最忙的時段」正規化的。所以金閣寺標成「2 級」，絕對人數可能還是爆滿。
- B 的外部驗證用京都觀光快適度地圖，但它是 KDDI 位置資料加 Prophet 模型的「預測值」，授權也不明。如果兩者相關高，那張地圖本身就是比照片更好的真值；如果相關低，G3 就失效。兩種結果 B 都輸。
- **追問**：通過門檻是多少？沒通過要怎麼辦？

**B-3：排除了最高頻的題型，核心卻依賴被排除的資料。**
- B 的範圍規則 R0 把營業時間、交通、時刻表全部排除。但下面三個來源都指出這些正是高頻題：
  - C 的 PTT 先導抽樣。
  - B 自己引用的 2019 年碩論：PTT Japan_Travel 7,001 篇裡，交通規劃與行程安排最常被討論。
  - Ram et al. 2021：8,905 則提問歸納出四個屬性，其中兩個是行程時間和服務可用性。
- B 的行程可行性題（P1、P2）又必須用到營業時間和路網時間，也就是 A 的知識庫。
- P1 用停留時間中位數，而這個數字以照片跨度為下界、本身就偏短。多站累積後，信賴區間可能超過 ±1 小時。B 打算用 30 分鐘的門檻刪掉難判的題，結果不是刪掉大半，就是留下重抽樣後答案會翻轉的題。

### 對 C（真實問題與網路文本派）

**C-1：關西的移動類題目大多無法用程式執行。**
- 本回合只找到京都市巴士的 GTFS（ODPT 的 CKAN 平臺；OSM wiki 標示 CC0）。JR 西日本、京阪、阪急、近鐵、京都地下鐵都沒找到 GTFS。
- 京都↔大阪、伏見稻荷、嵐山、奈良這些最常見的移動，都落在無法精算的範圍；「首末班」這類題根本無法執行。
- **追問**：Phase 0 的移動類原子題，有多少比例只靠開放資料就能算出答案？如果不到一半，「可驗證」實際上只剩營業時間和氣候兩類。

**C-2：成本和產率都被低估。**
- 一題 C4（行程可行性）要拆路段、查日文官網的營業時間、窮舉順序、保存證據，實際要 15–30 分鐘，不是 C 估的 3 分鐘。2,500 題算下來是 600–1,250 小時，不是 150 小時。
- C 自己的先導顯示：通用詞樣本裡 65% 不是時空題；地名樣本裡 78% 是長篇行程請益。
- **追問**：每 100 篇貼文能切出幾題「在範圍內、而且能執行」的原子題？

**C-3：標準不一致，新意也已被搶先。**
- C 批評 B 給的是統計答案，自己卻用一樣的統計做法：
  - 物候題（C6）用自訂的「開花日到滿開後 7 天」窗口，加上氣象台的一棵標本木，就要回答全京都任一地點「4/8 還看得到櫻花嗎」。
  - 氣候題（C7）是平年值查表，測的是記憶，不是推理。
  - 票券題（C3）是規則套用，不是時空推理。
- 「真實需求 + 網路文本 + 可驗證」這個組合已經有人做了：
  - [VeriTrip](https://arxiv.org/abs/2605.28683)（NeurIPS 2026）：非結構化網頁語料，加上可驗證的知識庫。
  - [TravelBench](https://aclanthology.org/2026.acl-long.1347/)（ACL 2026）：真實世界查詢，加上 10 個工具的快取沙盒。

## 2. 回應，以及我方修正
- **C 批評「模板題不真實」**：部分接受。我採用 C 的「雙胞胎題」設計（同一題同時有模板問法和真實問法，用來量化兩者的表現落差，以下稱真實性落差）和論壇頻率校準。另一方面，C 的 8 類裡有 5 類能直接對應到 A 的題型。兩派各自從不同來源歸納出相同的類別，這本身就說明這些題型常見。
- **B 批評「A 只能答靜態事實」**：部分接受。我做兩項修改：
  - 新增 T7 時段人潮，資料用臺北捷運各站分時進出量（[128506](https://data.gov.tw/dataset/128506)，OGDL，每月更新）。這是官方的全量計數，不是抽樣。
  - 「順路」和「住哪裡比較方便」併入 T4。

  停留時間仍只當作題目裡明示的參數，因為臺灣沒有可驗證的開放真值。
- **新意**：接受批評。我撤回第一回合引用 ChatPlanner「大眾運輸路徑規劃缺 benchmark」的說法：
  - [TransitLM](https://arxiv.org/abs/2605.22355) 用高德資料（北京、上海、深圳、成都，超過 1,300 萬筆），做「不用地圖、直接生成路線」的 benchmark。
  - MetroLLM-Bench 已經包含臺北捷運。

  A 的新意改成四點：
  1. 原子題同時涵蓋營業時間與活動、時刻表、多站軌跡三者，不只做大眾運輸。
  2. 題型互斥，附標註一致性 κ，並用真實題校準頻率。
  3. 知識庫採開放授權、可以重新生成，能抵抗訓練資料汙染。
  4. 能評估推理過程中的軌跡，而不只看最後答案。

  TransitLM 的路線生成做法可以當成一條對照基線。
- **我方站不住的地方**：
  - 觀光署景點資料集（7777）的授權欄沒查到，營業時間欄位（ServiceTimeInfo）的結構也還沒確認。
  - TDX 提供 GTFS，目前只有間接證據。
  - 臺北捷運只有班距（[131736](https://data.gov.tw/dataset/131736)）和首末班資料，沒有逐班時刻。所以含捷運的旅程只能給區間，或用最壞等待時間計算。
  - 第一回合的題型切法有兩處要修：
    - C2 的切法前後不一致。
    - C3 和 C4 的界線用「是否需要選路」來劃，標註者看不到這個條件。

## 3. 主持人指定議題

**(a) 地區**

| 面向 | 臺灣 | 京都／關西 |
|---|---|---|
| 題目來源量 | 中等：Mobile01 地區版（花蓮版 2026 年仍活躍）、r/taiwan 每週旅遊串；Dcard 和 PTT 未查證 | 高：PTT Japan_Travel、背包客棧、Dcard |
| 時空知識 | 高：TDX 涵蓋所有運具；另有臺鐵時刻表（6138）、捷運班距與首末班、觀光署景點/活動/餐飲、辦公日曆 | 低到中：只有京都市巴士 GTFS；鐵道 GTFS 沒找到；營業時間要靠 OSM 或官網 |
| 軌跡資料 | 個人軌跡可以由知識庫推算；群體有捷運分時進出量的全量資料 | 照片軌跡較多，但 Flickr API 只給 Pro、ToS 限制快取，小時尺度效度也未經驗證 |
| 授權 | OGDL（相容 CC BY 4.0）加上 ODbL，知識庫可以整包釋出 | 巴士 CC0；鐵道沒有開放資料；Flickr 只能釋出照片 ID |

**表態：核心選臺灣。** 四項中臺灣贏三項，而且研究生人在臺灣，可以到現場核對。我也接受 C 的論點，關西的題目量確實較大。所以把「京都市巴士 GTFS + OSM、只出巴士和步行題」列為延伸選項。

**(b) 軌跡的定位：一主一從。**
- **主**：個人計畫軌跡（T3、T5、T6）。答案是決定性的，每題附 gold 軌跡，可以評估推理過程。
- **從**：群體統計（T7）。只用官方全量計數，附週數 n 和穩定度。
- 照片推估的群體軌跡不拿來當標準答案。

**(c) 題型覆蓋**
- **納入**：營業與活動、班次、點到點旅程、條件式搜尋（含順路、住哪裡）、軌跡檢核、行程排序，以及只限捷運可達觀光站的時段人潮。
- **排除**：

| 題型 | 排除理由 |
|---|---|
| 停留時長 | 臺灣沒有可驗證的真值，列為延伸 |
| 照片推估的擁擠度 | 效度不足（見 B-2） |
| 票券 | 屬於規則套用，列為延伸 |
| 氣候、物候 | 屬於查表或統計 |
| 即時資訊、主觀推薦、自駕 | 無法用快照驗證，或沒有客觀答案 |

  B 把營業時間、交通、時刻表排除，這點是錯的（見 B-3）。

**(d) 邊界一致性**
- **A 的 C2**：接受批評。改用一致的切法，只分「查詢具名實體」和「條件式搜尋」兩種，實體是地點還是活動只是屬性，不再拿來分類。
- **A 的 C3／C4**：改用標註者看得到的語言線索：
  - 問「班次」（哪一班、下一班、末班、那班車幾點）歸 T2。
  - 問「我的旅程」（我幾點到、要多久、最晚幾點出發）歸 T3。
  - 替換測試：把問句換成「我最快幾點到」而意思不變，就歸 T3。
  - 先導階段單獨計算這一對的 κ，低於 0.8 就把 T2 併入 T3。
- **B 的 G3**：效度不足，建議改用全量計數，或只問時段排序。
- **C 的 C7 氣候**：屬於時空「資料」，但不是時空「推理」，排除。
- **C 的 C3 票券**：和軌跡有關，但本質是規則套用，列為延伸。

**(e) 一個人一年做得完嗎**
- B 和 C 的完整版各自都很重，三方全部合併做不完。
- 切法如下：

| 層級 | 內容 |
|---|---|
| 核心（必做） | A 的知識庫、T1–T6、神經符號代理，加上小規模真實題子集 |
| 條件式核心 | T7，第 1 個月的可行性檢查通過才納入 |
| 延伸（三選一） | 京都巴士子集、照片推估的停留時間、票券 |

## 4. 最終推薦

### 題目
- **中文**：可驗證的旅客時空與軌跡問答：以臺灣開放資料建構時空知識庫、真實提問校準的題型與神經符號代理
- **英文**：Verifiable Spatio-Temporal and Trajectory QA for Travelers: An Open-Data Knowledge Base, a Real-Question-Calibrated Taxonomy, and a Neuro-Symbolic Agent for Taiwan

### 地區
臺北都會區，加上全臺臺鐵與高鐵；跨區測試選花蓮或臺南其中一個。

### 核心資料來源
1. TDX：所有運具的時刻表與 GTFS，資料集標示 OGDL。
2. 臺鐵鐵路時刻表（data.gov.tw 6138）。
3. 臺北捷運：班距（131736）、首末班（131735）、分時進出量（128506）。
4. 觀光署景點、活動、餐飲（7777、7778、7779）。
5. OSM 臺灣（Geofabrik，ODbL）。
6. 行政機關辦公日曆表（14718）。
7. 真實題：Mobile01 地區版、r/taiwan 每週旅遊串、自辦問卷；Dcard 和 PTT 要先確認站方條款。
8. 工具：OTP2（LGPL）、opening_hours.js。

### 題型（7 類）

| 類別 | 給定 → 問 → 答案型別 | 標準答案怎麼算 | 例題 |
|---|---|---|---|
| T1 具名實體時間查詢 | 一個具名的地點或活動，加上時刻或日期 → 有沒有開、開放時段、何時舉辦 → Bool 或時間區間 | 營業規則（opening_hours 語法）加辦公日曆計算；活動看日期區間是否交集 | 故宮下週一有開嗎？ |
| T2 班次時刻 | 一個站（可加路線、方向、迄站）加上時刻，或一班已指明的車 → 下 k 班、首末班、那班車的到站時刻 → 時刻清單 | GTFS 先篩出當天有開的班次，再排序各站時刻；不做選路 | 新竹站下一班往臺北的區間車幾點？ |
| T3 點到點旅程 | 起點、一個終點、出發時刻或期限（期限可以由 T1 推出）→ 幾點到、要多久、最晚幾點出發、轉幾次、趕不趕得上 → 時刻、分鐘、整數或 Bool | RAPTOR 或 OTP 算最早抵達，反向算最晚出發；附 gold 行程段；遇到班距制路線時給區間 | 明早 9 點從臺北車站出發，最快幾點到九份？ |
| T4 條件式搜尋 | 錨點（一個點，或一組起訖代表的路線）、目標類別或候選清單、界限（距離、時間、繞路多少、總旅行時間），可加營業或活動條件 → 地點集合、最佳者或數量 | 路網等時圈；順路的條件是繞路後增加的時間不超過指定值；「住哪裡」比較到各目的地的總旅行時間，差距在 5% 內算並列 | 臺北車站到淡水途中，繞路 30 分鐘內可以去哪？ |
| T5 軌跡檢核與推算 | 至少 2 個有順序的目的地、出發時刻、各站停留時間、運具 → 可不可行、第 k 站幾點到、幾點結束、第一個出問題的站 → Bool 加站序，或時刻 | 從頭往後模擬，每一站的停留時段都必須落在開放時間內 | 10 點出發，中正紀念堂和國父紀念館各待 1 小時，16 點前到得了 101 嗎？ |
| T6 行程排序 | 2–5 個沒有順序的地點、起點、停留時間、期限 → 最佳順序、最多能去幾個、能否全去 → 序列、整數或 Bool | 窮舉所有順序，每種都用 T5 的方法模擬；先比能去幾個，再比誰結束最早；接受任一最佳解 | 下午 1 點出發，故宮、士林夜市、北投溫泉博物館怎麼排？ |
| T7 時段人潮 | 捷運可達的景點、日子類型（平日、週末、國定假日）、候選時段 → 哪個時段人最多或最少、兩個時段比較 → 時段或 Bool | 取近 N 週出口站分時出站量的平均；第一名在至少 80% 的週次都維持第一才收題；附 n | 週六去淡水，哪個兩小時時段人最少？ |

### 依序決策規則（第一條成立就停）
- **R0**：把多意圖的問題拆成原子題，並濾掉範圍外的題。
- **R1**：問人多人少、哪個時段擠 → T7。
- **R2**：要評估一趟行程造訪多個地點的可行性或時間軸。順序已給 → T5；順序沒給（包括「哪個先去」）→ T6。
- **R3**：要從類別或候選中選出地點或活動（附近有什麼、哪個近、順路、住哪裡）→ T4。
- **R4**：問的是班次 → T2。
- **R5**：問的是「我從 A 到 B」的旅程 → T3。
- **R6**：問單一具名實體的時間屬性 → T1。
- 都不符合的標為「未覆蓋」；這類若佔 5% 以上，就回頭新增類別。

### 排除清單
- 即時資訊：誤點、即時人潮。
- 停留時長的估計。
- 照片推估的擁擠度。
- 票價與票券。
- 氣候、物候、日出日落。
- 主觀推薦。
- 自駕與停車。
- 多日行程規劃。

### 系統
1. LLM 把問題轉成 DSL。
2. 實體連結用中英別名表；時間正規化時查辦公日曆。
3. 交給執行器計算：OTP2 或 RAPTOR、opening_hours.js、PostGIS、DuckDB（處理進出量資料）。
4. 回答時附上推導軌跡、知識庫版本和樣本數 n；證據不足時拒答。
5. 另做一個小模型版本：用 LoRA 微調 7B 開源模型來做第 1 步的解析。

### 基線
- 不給工具的 LLM，以及不用地圖直接生成路線（TransitLM 式）。
- 文本 RAG（C 派做法）。
- 用 ReAct 直接呼叫原始 API。
- 直接寫程式查 GTFS 的 code agent（TransitGPT 式）。
- 上界：給正確的 DSL，再交給執行器。

### 評估指標
- 各類答案：完全比對、集合 F1、與最佳解的差距。
- 推理過程：DSL 槽位 F1、實體連結正確率、時間正規化正確率、軌跡是否有效。
- 雙胞胎題的真實性落差，用 McNemar 檢定。
- 答對 +1、拒答 0、答錯 −1 的計分，懲罰亂答。
- 反事實一致性：把日期改成國定假日，答案應該跟著變。
- 成本。
