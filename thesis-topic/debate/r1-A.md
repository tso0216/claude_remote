# 立場 A「結構化時空知識庫派」第一回合立論

**查證方式先說明**：本 session 的 WebFetch 連不到 data.gov.tw 和 bookdown.org（會被網路設定擋下，要在 session 網路設定放行後才能直接開頁）。所以下文的「已查證」都是用 WebSearch 的結果摘要核對的；沒查到的地方標「未查證」。

## 1. 題目與一句話主張
- **中文**：可驗證的旅客時空問答：以臺灣開放資料建構時空知識庫、互斥題型與神經符號代理
- **English**：Verifiable Spatio-Temporal QA for Travelers: An Open-Data Knowledge Base, a Disjoint Question Taxonomy, and a Neuro-Symbolic Agent for Taiwan
- **主張**：旅客最常問的時空問題（幾點開、下一班幾點、多久到、附近有什麼、這樣排來得及嗎）本質上都是「在時刻表和營業時間的約束下做計算」。所以答案應該由程式從開放資料算出來，而不是靠人工標註，也不是從網路文本抽出來。

## 2. 研究問題與貢獻
**研究問題**
- **RQ1**：常見的旅客時空問題，能不能切成互斥、可以用規則判定的題型？衡量方式是標註者一致性 κ 和真實題的覆蓋率。
- **RQ2**：LLM 在哪個環節失敗？候選環節有：相對時間正規化、營運日曆、轉乘、營業規則、多站組合。
- **RQ3**：「LLM 把問題轉成 DSL，再交給符號引擎執行」的代理，準確度和可驗證性是否勝過 closed-book、文本 RAG 和 code agent？小模型微調後能否追上大型模型？

**貢獻**
1. 7 類互斥題型和依序決策規則，並用真實問題校準各類的頻率。
2. 資料集 TaiwanSTQA（暫名）：
   - 一份開放授權的時空知識庫快照。
   - 約 1 萬題程式驗算過的中英問答，每題附 gold 軌跡。
   - 生成器一起開源。換日期或換快照就能重新出題，降低題目被模型訓練資料汙染的風險。
3. 神經符號代理，加上 oracle-DSL 錯誤歸因：把錯誤拆成「解析錯」和「推理錯」兩部分。

## 3. 資料集設計
### 地區：臺灣
理由：
- **一個平臺涵蓋所有運具**：TDX 單一平臺就有臺鐵、高鐵、捷運、公車和觀光資料。
- **授權可再散布**：TDX 和觀光署的資料集在 data.gov.tw 標示「政府資料開放授權條款 v1.0（OGDL）」。這個條款明文和 CC BY 4.0 相容，可以再散布，但必須照附件格式「顯名」。
- **假日可精確判定**：有官方辦公日曆，國定假日和補班都查得到。
- **可能是空白**：本回合搜尋沒看到以臺灣開放資料、繁中為主的時空旅遊 QA（這不代表一定不存在）。

範圍與語言：
- 全臺臺鐵和高鐵都納入。
- 深度區是臺北都會區；泛化測試區在花蓮或臺南之間擇一。
- 繁中 80%，英文 20%（模擬來臺旅客）。
- 其他地區（例如日本）本回合沒有查證，所以不推薦。

### 資料層次
| 層 | 內容 |
|---|---|
| L0 空間 | OSM 步行路網、站點、POI 座標 |
| L1 時間屬性 | POI 營業規則（正規化成 OSM `opening_hours` 語法）、活動起訖時間、辦公日曆 |
| L2 時刻 | GTFS（臺鐵、高鐵、公車）、捷運首末班與班距 |
| L3 軌跡 | 帶時間戳的序列 ⟨(地點, 抵達, 離開, 交通段)⟩，由 L0–L2 推出，作為 C4、C6、C7 的 gold |

### 建構流程
1. **擷取並凍結快照**：固定一段 4 週的服務期，記下 kb_version。
2. **實體對齊**：把觀光署 POI 和 OSM 對起來（名稱加距離），建立中英別名表。
3. **營業時間正規化**：
   - 用 LLM 把自由文字轉成 `opening_hours` 語法。
   - 用 opening_hours.js 檢查能不能解析。
   - 分層抽 300 筆做人工核對。
   - 不合格的 POI 不出 C1、C6、C7 的題目。
4. **ground truth 引擎**：OTP2 或自寫的 RAPTOR、`opening_hours` 評估器、PostGIS。
5. **出題**：模板加分層抽樣，涵蓋平日和假日、尖峰時段，以及臨界情況（快關門、末班車、跨午夜）。每題附 `asked_at`。
6. **改寫**：LLM 改寫成多種口吻，再做 round-trip 檢查：從改寫後的句子重新抽 slot、重新計算答案，跟原答案一致才收。
7. **測試集**：全部人工驗證。

### 規模與切分
- 訓練與開發集約 1 萬題（可以拿來微調）。
- 測試集 1,400 題（7 類各 200 題，人工驗證）。
- 真實題子集 300–500 題，用 KB 重新作答。
- 切分方式三種：同區、跨區、未見模板。

## 5. 題型分類
**符號定義**
- open(p,t)：依正規化後的營業規則和辦公日曆（國定假日），地點 p 在時刻 t 是否開放。
- EA(o,d,t,M)：從 o 在時刻 t 出發、用運具 M，最早幾點到 d（時間相依）。
- LD：反過來算，最晚幾點出發才能準時到。

| 類別 | 給定 → 問 | 答案型別 | ground truth 算法 | 例題 |
|---|---|---|---|---|
| C1 營業時段 | 一個有名字的常設地點，加上時刻或日期 → 有沒有開、當天開放時段、幾點關 | Bool 或時間區間 | 用正規化規則加辦公日曆計算 open(p,t) | 「故宮下週一有開嗎？」 |
| C2 活動期間 | 一個有名字的活動，或「區域/半徑 + 日期區間 D」→ 何時舉辦、D 內有哪些活動 | 時間區間或活動集合 | 活動的 [Start, End] 和 D 有交集，再用 EventStatus 篩選 | 「這週末臺北有哪些燈節活動？」 |
| C3 班次時刻 | 一個站（可加路線、方向、迄站）加時刻，或已指明某班車 → 下 k 班、首班或末班、那班車到某站的時刻 | HH:MM 清單 | GTFS：用 calendar 篩出當天有開的班次，取出發時刻 ≥ t 的 stop_times 排序。不做路徑搜尋 | 「新竹站下一班往臺北的區間車幾點？」 |
| C4 點到點旅程 | 起點、單一終點、出發時刻或期限（期限可以由 C1 或 C2 推得）、運具 → 抵達時刻、所需時間、最晚出發、轉乘次數、趕不趕得上 | 時刻、分鐘數、整數或 Bool | 用 RAPTOR 或 OTP 算 EA，反向算 LD；附 gold 行程段 | 「明早 9 點從臺北車站搭大眾運輸，最快幾點到九份老街？」 |
| C5 周邊與可達 | 一個錨點、一個類別、一個界限（距離、步行時間或大眾運輸時間），可加「抵達時還開著」→ 符合的地點集合、最近的一個、或數量 | POI 集合、單一 POI 或整數 | 路網距離，或從錨點出發的等時圈，再交集類別和 open | 「西門站走路 10 分鐘內，現在還開著的博物館有哪些？」 |
| C6 軌跡檢核與推算 | 有順序的行程 o→p₁→…→pₙ（n ≥ 2）、出發時刻、每站停留時間、運具 → 可不可行、第 k 站幾點到、幾點結束、第一個出問題的是哪一站 | Bool 加站序與原因，或時刻 | 從頭往後模擬：aᵢ = EA(pᵢ₋₁, pᵢ, aᵢ₋₁ + dwellᵢ₋₁)；要求從抵達到離開的整段 [aᵢ, aᵢ+dwellᵢ] 都在開放時間內 | 「10 點從臺北車站出發，中正紀念堂待 1 小時、國父紀念館待 1 小時，16 點前到得了 101 嗎？」 |
| C7 行程排序 | 沒有順序的地點集合（2 ≤ n ≤ 5）、起點與出發時刻、停留時間、期限 → 最佳順序、最多能去幾個、能不能全部去 | 序列、整數或 Bool | 窮舉所有順序（最多 5! = 120 種），每種用 C6 的模擬器評估。目標依序是「造訪數最多」，其次「結束最早」。ground truth 是最佳解的集合 | 「下午 1 點從臺北車站出發，故宮、士林夜市、北投溫泉博物館怎麼排最快逛完？」 |

### 依序決策規則（從 R0 往下判斷，第一條成立就停）
- **R0**：多意圖的問題先拆成單一意圖的原子問題。主觀、即時、票價、天氣、擁擠類的問題直接排除。
- **R1**：有兩個以上目的地，而且順序已定 → C6。
- **R2**：有兩個以上目的地，但順序未定 → C7。
- **R3**：問的是大眾運輸「班次本身」的時刻（某站的下一班、首末班、已指明那班車的到站或發車時刻），不需要選路 → C3。
- **R4**：有起點和單一終點，問的是這趟旅程的結果（幾點到、要多久、最晚幾點出發、轉幾次、趕不趕得上）→ C4。
- **R5**：要找的是沒有指名的常設地點，用類別加上空間或時間界限篩選 → C5。
- **R6**：對象是有起訖時間的活動 → C2。
- **R7**：一個有名字的常設地點，問它的開放狀態或時段 → C1。

**邊界示例**
- 「臺北到臺中下一班高鐵幾點開」→ C3；「臺北到臺中最快幾點到」→ C4。
- 「最近還開著的夜市」→ C5；「饒河夜市幾點開」→ C1。

### 憑什麼說這些類別「常見」
1. **文獻**：
   - Gal-Tzur et al. 2018（*Travel Behaviour and Society* 10:1–9）：TripAdvisor 問答區的交通問題可以自動分類，也能抽出起訖點。https://cris.haifa.ac.il/en/publications/an-improved-methodology-for-extracting-information-required-for-t/
   - Ram, Gal-Tzur, Rechavi 2021（*J. Transport Geography*）：分析 8,905 則都市大眾運輸提問，歸納出四個屬性，其中包括「行程時間」和「服務可用性」。https://www.x-mol.com/paper/1389398364882231296
   - Hwang, Jani, Jeong 2013（*JBR* 66(6)）：分析旅遊論壇中的功能性資訊需求。
   - 注意：這三篇各類別的具體百分比我都沒有查到。
2. **獨立的 benchmark 收斂到相近的類別**：TransitGPT 分 8 類；MapEval 涵蓋地點資訊、周邊、路線、行程等任務。
3. **自行校準，而且可以被推翻**：
   - 從 Q2、Q3 抽 500 則以上的真實問題，加上問卷。
   - 兩人依上面的規則各自標註，目標 κ ≥ 0.8，用來證明類別邊界清楚。
   - 任一類若佔時空問題不到 3%，就刪除或併入其他類。

### 刻意排除的題型
- 即時資訊：誤點、即時到站、擁擠程度。
- 主觀推薦。
- 票價與訂位：常見但不屬於時空問題，留作延伸。
- 天氣、日出日落。
- 自駕與停車。
- 多日行程規劃：答案不唯一，而且已有 TravelPlanner 等 benchmark 在做。
- 無障礙路線、YouBike 即時車位：罕見或屬動態資料。

## 6. 系統設計與評估
### 架構
1. **解析**：輸入問題加 `asked_at`，由 LLM 轉成 DSL。DSL 有 7 個運算子：`open_at`、`events`、`departures`、`journey`、`search`、`simulate`、`best_order`。
2. **前處理**：實體連結（中英別名表加 embedding 檢索）和時間正規化（相對時間轉絕對時間，查辦公日曆）。
3. **符號執行**：OTP2 或 RAPTOR、opening_hours 評估器、PostGIS。
4. **回答**：LLM 用執行結果寫回答，並附上推導出的軌跡。
5. **重試**：執行時出錯（找不到實體、無解）就把錯誤回饋給 LLM 重新解析，最多 2 次。
6. **小模型變體**：用 LoRA 微調一個 7B 開源模型當解析器，一般 GPU 就能跑。

### 基線
- **B0 closed-book LLM**：商用和開源模型都測。
- **B1 文本 RAG**：把同一個 KB 轉成文字文件再做檢索，等於 C 派的做法。
- **B2 ReAct 工具代理**：直接呼叫原始 API，類似 TravelPlanner 的設定。
- **B3 code agent**：TransitGPT 式，讓模型直接對 GTFS 或 CSV 寫 Python。
- **上界**：給正確的 DSL，再交給執行器。

### 指標
- **答案正確性**：
  - Bool 和時刻用完全比對。純時刻表的題不容許誤差；含步行的題容許 ±3 分鐘；班距制的路線只出區間題。
  - 所需時間看相對誤差。
  - 集合答案看 F1。
  - 序列答案看三項：可不可行、和最佳解差多少、有沒有落在最佳解集合裡。
- **過程**：DSL 槽位 F1、實體連結準確率、時間正規化準確率、軌跡有效率（模型給出的軌跡能不能通過檢核器）。
- **穩健性**：
  - 改寫一致性：同一題換說法，答案應該一樣。
  - 反事實一致性：把日期改成國定假日，答案應該跟著變。
  - KB 外的問題要能拒答。
- **成本**：token 數和延遲。
- **真實性**：另外報告真實題子集和合成題之間的表現落差。

## 7. 與既有研究的差異
- **行程規劃型 benchmark**：TravelPlanner（https://arxiv.org/abs/2402.01622 ，1,225 題）、ChinaTravel（https://arxiv.org/abs/2412.13682 ，ICLR 2026，用 DSL 驗證）、TripCraft（https://arxiv.org/abs/2502.20508 ，ACL 2025，美國 140 個城市，含大眾運輸時刻）、WorldTravel（https://arxiv.org/abs/2602.08367 ）、NATURAL PLAN（https://arxiv.org/abs/2406.04520 ）。
  - 這些評的都是開放式「生成行程」，用檢核器打分，答案不唯一。
  - 本案做的是原子化 QA，每題都有唯一的程式解；而且把這些 benchmark 用來打分的「軌跡檢核」本身變成題型 C6。
- **地圖 QA**：MapEval（https://arxiv.org/abs/2501.00316 ，700 題選擇題）、MapQaTor（https://arxiv.org/abs/2412.21015 ）。
  - 這兩者依賴外部地圖 API 和人工出題。
  - 本案用開放授權的 KB、程式算答案、開放式作答，而且包含時刻表推理。
- **大眾運輸加 LLM**：ChatGPT for GTFS（https://arxiv.org/abs/2308.02618 ）、TransitGPT（https://arxiv.org/abs/2412.06831 ）、ChatPlanner（https://arxiv.org/abs/2606.15315 ）、MetroLLM-Bench（https://arxiv.org/abs/2609.10016 ，955 題）。
  - 這些只處理運輸本身，沒有營業時間、活動和多站軌跡。
  - ChatPlanner 指出大眾運輸路徑規劃目前缺少 benchmark；它也報告 GPT-5 加上地圖工具，端到端的可行率只有約 1/3。
- **方法先例**：ToolQA（https://arxiv.org/abs/2306.13304 ）、KQA Pro（https://arxiv.org/abs/2007.03875 ）都是「模板 + 程式算答案 + 改寫」。本案把這套做法搬到時間相依的路網上。
- **軌跡加 LLM**：LLM-Mob（https://arxiv.org/abs/2308.15197 ）、TrajAgent（https://arxiv.org/abs/2410.20445 ）、STBench（https://arxiv.org/abs/2406.19065 ）預測或分析的是「已觀測到的」軌跡；本案把軌跡當成要檢核、要推算的計畫。
- **旅遊 QA**：TourismQA（https://arxiv.org/abs/2009.13613 ）偏推薦，答案依據是評論文本。

## 8. 最大風險，以及為什麼仍優於 B、C
### 最大風險
營業時間資料品質不佳（自由文字、可能過時），加上捷運和部分公車是班距制，會壓縮「答案精確」的題目數量。對策：
- **採快照語意**：ground truth 定義為「相對於某個 KB 版本的正確答案」，跟 KQA Pro、ToolQA 的做法一樣。
- **公開 KB 本身的準確率**：抽樣比對官網並把結果寫進論文。
- **精確題只出時刻表制的班次**（臺鐵、高鐵、時刻表制客運）；班距制的路線只出區間題。

### 次要風險
- **合成題不自然**：用改寫、人工驗證、真實子集來處理，並公開合成題和真實題之間的落差。
- **新意被質疑**：見第 7 節。

### 對 B（群體軌跡派）
- 「停留多久、看完 A 接哪裡、何時人多」的答案，是從有偏樣本（會拍照、會打卡的人）得到的統計估計。結果會隨停留點的判定門檻改變，沒有唯一、可驗證的 ground truth。
- 個人軌跡涉及隱私，平台條款可能限制再散布。這部分我沒有查證，留給 B 舉證。
- 這些多半是推薦型需求，不是高頻的原子問題。
- B 的資料可以拿來當 C6、C7 的預設停留時間，但本案的 ground truth 不需要依賴它。

### 對 C（真實問題與網路文本派）
- **論壇的題型分布有選擇偏差**：例行的時刻、路線問題，旅客多半直接用地圖 App 解決；會發到論壇的偏向非例行、多意圖、主觀的問題。所以論壇頻率不等於旅客的需求頻率。
- **ground truth 難擴充**：答案要人工標註，又會過時，很難做到上萬題。
- **文本 RAG 不會算時間和轉乘**：GTFS 的複雜查詢，GPT-4 即使用程式合成，準確率也只到 61%；ChatPlanner 也報告端到端可行率只有約 1/3。
- 本案已經吸收 C 的長處（用真實題校準、保留真實子集），但答案仍由程式計算。
