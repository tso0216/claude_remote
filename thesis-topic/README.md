# 論文方向定案：可驗證的旅客時空與軌跡問答（臺灣）

> 由三位辯手經三回合辯論產生（立論 → 交叉質詢 → 審查主持人草案），本檔是主持人依第三回合審查意見修正後的定案。完整辯論紀錄在 [`debate/`](debate/)。
> 文中「已查證」指辯論期間用網路搜尋確認過；本環境連不到 data.gov.tw、TDX、PTT，所以欄位細節要在第 1 個月自己下載確認（見 §10）。

## 0. 結論

- **題目（中）**：可驗證的旅客時空與軌跡問答：以臺灣開放資料建構知識庫、真實提問校準的互斥題型與神經符號代理
- **題目（英）**：*Verifiable Spatio-Temporal and Trajectory QA for Travelers: An Open-Data Knowledge Base, a Real-Question-Calibrated Disjoint Taxonomy, and a Neuro-Symbolic Agent for Taiwan*
- **主張**：旅客最常問的時空問題（幾點開、怎麼去、排得完嗎、怎麼排、附近哪裡、要待多久／幾點人少）可以切成 **6 類互斥的原子題**。每一類都能從網路開放資料用程式算出可驗證的答案。把問題轉成 DSL、交給符號執行器的代理，比 closed-book 和文本 RAG 更準，也更知道何時該拒答或反問。
- **地區**：臺北都會區是深度區，另含全臺臺鐵與高鐵的城際交通；跨區測試選花蓮或臺南。若第 1 個月真實提問不夠，依 §9 的關卡改做京都。
- **「軌跡」的定位：一主一從**
  - **主：旅客自己的計畫軌跡**（Q3、Q4，Q2 是它的基本運算）。每題附 gold 軌跡，也就是帶時間戳的序列 ⟨地點, 抵達, 離開, 交通段⟩，所以能評估推理過程，不只看最後答案。
  - **從：群體軌跡與流量**（Q6）。停留時間分布從遊記軌跡抽出；時段人潮用捷運分時進出量。群體常模同時是 Q3 在題目沒給停留時間時的參數。
  - 遊記抽出的真實行程，用來決定 Q3、Q4 題目裡的地點組合，讓組合來自真實旅客，而不是隨機拼湊。

- **地區仍有分歧**：A 主張臺灣；B、C 主張京都，但兩人都附上退回臺灣的關卡。

### 第三回合：審查主持人草案（預設臺灣）

- **整體設計**：三位都是有條件同意。
- **地區預設臺灣**：A 同意，B、C 有條件同意，條件是加上對稱的關卡，提問量不夠就改做京都。
- **採納的修正**：
  - Q2、Q3 改用「有沒有停留」切開。
  - 日出日落納入 Q1。
  - 修正「住哪裡」被誤判成排序題的問題。
  - Q2 加入「候選路線比較」這個答案型別。
  - 新增「需澄清」標籤。
  - 剝除主觀修飾詞後再分類。
  - 多日行程拆成每天一題。
  - 停留時長與時段人潮合併成「群體常模」一類。
  - 建立預設解讀表。
  - 抽核知識庫準確率，並報告兩種分數。
  - 真實子集每類至少 100 題。
  - 依族群分層抽樣與報告。

**為什麼預設臺灣**：

1. 使用者說「題目可以自己想」，所以真實題只用來校準頻率和組成真實子集，不需要海量來源。
2. 臺北捷運分時進出量是官方的全量計數，比照片推估的人潮可靠。
3. 觀光署的活動資料有結構化的起訖時間。
4. 知識庫可以用 OGDL 加 ODbL 整包釋出。
5. 不必等外部單位核准。
6. 研究生在臺灣，可以實地核對。

**臺灣的弱點**（三位都同意，已用 §9 的關卡處理）：

- 繁中國內旅遊的提問量偏少，論壇上多是遊記和心得。
- 捷運和多數市區公車是班距制，只能給區間答案。
- 觀光署的營業時間是自由文字，而且還留著已停業的點位。

## 2. 研究問題與貢獻

### 研究問題

- **RQ1**：旅客常見的時空問題，能不能切成互斥、只看題面就能判定的原子題型？
  - 衡量方式：標註一致性 κ、真實題覆蓋率、各類頻率。
- **RQ2**：LLM 在哪個環節出錯？候選環節有：
  - 實體連結
  - 相對時間正規化
  - 營業規則與國定假日
  - 時刻表與轉乘
  - 多站組合
  - 群體常模的不確定性
  - 該拒答或反問時沒有做到
- **RQ3**：神經符號代理，對上 closed-book、文本 RAG、ReAct、code agent：
  - 在合成題與真實題上差多少（realism gap）？
  - 用 LoRA 微調的小模型能不能追上？

### 貢獻

1. **題型與判定規則**：6 類互斥題型，加上依序判定規則和預設解讀表；各類頻率用真實提問校準，並報告 κ。
2. **資料集 TaiwanSTQA（暫名）**：
   - 可整包釋出的時空知識庫快照。
   - 約 1 萬題程式驗算過的問答，每題附 gold 軌跡、明示假設和 kb_version。
   - 真實子集、「不可答」子集、「需澄清」子集。
   - 生成器開源，換一份快照就能重新出題，抵抗訓練資料汙染。
3. **神經符號代理與完整評估**：
   - oracle-DSL 錯誤歸因。
   - 反事實測試：把日期改成國定假日，答案應該跟著變。
   - 拒答與反問。
   - 知識庫抽核後的兩種分數。
   - 時效漂移。

## 3. 資料集設計

### 知識庫分層

| 層 | 內容 |
|---|---|
| L0 空間 | OSM 步行路網、站點、POI 座標、中英別名表 |
| L1 時間屬性 | 營業規則（正規化成 OSM `opening_hours` 語法）、活動起訖、辦公日曆（國定假日、補班）、日出日落 |
| L2 時刻 | 臺鐵、高鐵、公車 GTFS；捷運首末班與班距 |
| L3 群體 | 捷運分時進出量的匯總；遊記抽出的停留分布 |

### 建構流程

1. **凍結快照**：固定一個 4 週的服務期，記下 kb_version。
2. **實體對齊**：把觀光署 POI 和 OSM 對起來，用名稱加距離比對。
3. **營業時間正規化**：
   - 用 LLM 把自由文字轉成 `opening_hours` 語法，再用 opening_hours.js 驗證能否解析。
   - 抽 300 筆人工核對。
   - 不合格的 POI 不拿來出 Q1、Q3、Q4、Q5 的題。
4. **標準答案引擎**：OTP2 或 RAPTOR、opening_hours 評估器、PostGIS、DuckDB、行程模擬器、排列窮舉器。
5. **出題**：
   - 每類一組模板，分層抽樣：平日與假日、尖峰、快關門、末班車、跨午夜等臨界情況。
   - 每題記錄提問時間（asked_at）和所有用到的預設值。
6. **改寫**：用 LLM 改寫成多種口吻，再做 round-trip 檢查：從改寫後的句子重新抽 slot、重新計算答案，跟原答案一致才收。
7. **真實題**：原子化 → 依規則分類 → 標註 EQR → 依 asked_at 重新對應到快照 → 由程式算答案。

### 規模與切分

- 訓練與開發集：約 1 萬題，可以拿來微調。
- 測試集：6 類 × 200 題，全部人工驗證。
- 真實子集：每個保留下來的類別至少 100 題，約 600 題以上。論壇題不夠的部分用徵集題補，真實子集的結果列為主要結果。
- 不可答子集與需澄清子集。
- 切分方式：跨區（花蓮或臺南）、沒看過的模板、用新快照重新生成的題目；真實題依發文時間切分。

### 釋出

- 知識庫：OGDL 資料附顯名聲明；OSM 衍生的資料遵守 ODbL。
- 論壇內容只釋出貼文 ID，加上我們自己寫的原子題和標註。

## 5. 題目類型（6 類）

### 5.1 設計原則

1. **分類單位是原子題**：一題只問一個目標，多意圖的問題先拆開。
2. **判定只看題面**：每條判定規則都只用題面上看得到的線索，不用「需不需要選路」這種演算法性質。
3. **一類對應一個程式**：每一類對應一個可執行的程式模板，同一類的標準答案算法一致。
4. **只收常見題**：類別要過 Phase 0 的頻率門檻才保留（見 §5.7）。

### 5.2 定義

| 類 | 給定 → 問什麼 → 答案型別 | 標準答案怎麼算 | 例題 |
|---|---|---|---|
| **Q1 指名對象時間屬性** | 1 個指名的地點或活動，加日期或時刻 → 有沒有開、開放時段、幾點關、最後入場、活動哪幾天、日出日落 → Bool、時間區間、日期區間或時刻 | 用 `opening_hours` 規則加辦公日曆評估；活動看起訖日期；日出日落用氣象署資料或天文演算法 | 故宮下週一有開嗎？淡水這週六幾點日落？ |
| **Q2 單程移動** | 起點加 1 個終點，或 1 站加路線方向，可附出發時刻、抵達時刻或期限；**題目沒有停留** → 下一班、首末班、最早幾點到、要多久、最晚幾點出發、轉幾次、趕不趕得上、哪條路線比較快 → 時刻、分鐘、整數、Bool，或「選項加各自時間」 | GTFS 加 RAPTOR 或 OTP2，再加 OSM 步行。班距制的路線給區間。「趕得上」只對一個時間點判斷：有最後入場時間就用它，沒有就用閉館時間 | 明早 9 點從臺北車站出發，最快幾點到九份？去九份搭 1062 還是火車到瑞芳轉公車比較快？ |
| **Q3 行程時間軸** | 2 個以上、順序已定的目的地；或 1 個目的地但題目寫明停留時間、問「逛完幾點」、或問「X 半天／一天夠嗎」。另給出發時刻，可附截止時間。限單日 → 可不可行、第 k 站幾點到、幾點結束、哪一站先出問題 → Bool 加出問題的站、時刻，或三值（可行／不可行／視停留而定） | 逐站往後模擬（用 Q1 的規則和 Q2 的引擎），每一段停留都必須落在開放時間內。題目沒給停留時，用 Q6 停留區間的上界和下界各模擬一次，兩次結論不同就答「視停留而定」 | 10 點從臺北車站出發，中正紀念堂、國父紀念館各待 1 小時，16 點前到得了 101 嗎？象山看完夕陽再去饒河夜市還來得及嗎？ |
| **Q4 行程排序** | 2–5 個沒排順序的目的地，加起點、出發時刻，可附停留時間和截止時間。限單日 → 最佳順序、最多能去幾個、能不能全部去 → 序列、整數或 Bool | 窮舉所有排列（最多 5! = 120 種），每一種都用 Q3 的模擬器評估。比較順序：先看可不可行，再看造訪數多寡，最後看誰結束得早。和最佳解差 5 分鐘以內都算對 | 下午 1 點從臺北車站出發，故宮、士林夜市、北投溫泉博物館怎麼排？先去九份還是十分？ |
| **Q5 條件式找地點** | 一個錨點（一個點、一條起訖路線，或一組候選起點／住宿），加類別或候選，再加約束（距離、步行或運輸時間、繞路上限、某時刻有營業、某段期間有活動）→ 有哪些、哪個最近或最好、順路可以去哪、住哪裡比較方便 → 地點集合，或單一地點加各自的數值 | 路網距離或等時圈，再依條件過濾。「順路」＝繞路增加的時間不超過上限。「住哪裡」＝比較到各目的地的總旅行時間，相差 5% 以內算並列。集合題用 F1 或 valid@k 評分 | 西門站走路 10 分鐘內、晚上 9 點還開的博物館有哪些？住臺北車站還是西門，去九份跟淡水比較方便？ |
| **Q6 群體常模**（兩個子型分開計分） | 1 個地點，可附日型和候選時段 → (a) 一般待或逛多久；(b) 同一地點哪個時段人比較少或比較多，或某時段比該站其他時段擠多少 → (a) 時長區間（<1h、1–2h、2–4h、半天、一天）；(b) 時段、Bool 或相對等級 | (a) 遊記抽出的停留分布：抽取器要先在人工標註集上驗證，樣本數 n ≥ 30，而且至少兩個平台的結果一致才收題。(b) 用捷運分時資料，只用觀光型車站（週末對平日比高的站），只比可以遊覽的時段，取近 N 週平均，第一名在 80% 以上的週次都維持第一才收題；只做同一地點內的相對比較 | 九份老街一般逛多久？週六去淡水，下午 2 點和傍晚 6 點哪個人少？ |

### 5.3 依序判定規則（第一條成立就停）

- **R0 前處理**（依序做）：
  1. 原子化：把問題拆到每題只問一件事。
  2. 剝除主觀修飾詞：拿掉「好吃」「值得」這類詞之後，還有可計算的條件，就照常分類，但只計分那些條件；什麼都不剩就排除。
  3. 落在排除清單（§5.6）裡的 → 排除。
  4. 多日行程：已經分好哪天去哪裡 → 每天拆成一題；要系統自己分配天數 → 排除。
  5. 缺必要資訊（例如沒說哪一站的末班車）→ 標「需澄清」。
- **R1**：答案是「其他旅客在單一地點」的行為量，也就是一段停留時長，或一個時段或擁擠程度 → **Q6**。
- **R2**：問的是旅客自己的目的地本身的時間軸、可行性或順序：
  - 2 個以上目的地，而且順序沒定或問先後 → **Q4**。
  - 2 個以上已排好順序的目的地，或 1 個目的地但有停留（寫明停留時長、問逛完幾點、問「X 半天／一天夠嗎」）→ **Q3**。
- **R3**：答案是要從類別或候選中找出、選出的地點，包括附近、順路、住哪裡 → **Q5**。
- **R4**：只有 1 個目的地（或 1 站加方向），沒有停留，問的是移動 → **Q2**。
- **R5**：1 個指名地點或活動的時間屬性 → **Q1**。
- **R6**：以上都不符合 → 標「未覆蓋」。Phase 0 中若這類佔 5% 以上，就新增類別。
- **另外**：題型能判定，但知識庫沒有資料可以回答（例如九份的時段人潮）→ 標「不可答」，用來評估模型會不會拒答。

### 5.4 預設解讀表（出題程式與受測系統共用同一份，公開）

| 題目沒講清楚的部分 | 預設解讀 |
|---|---|
| 「幾點到」，但沒指定班次或車種 | 最早抵達 |
| 「來得及／趕得上（去 X）嗎」，沒講停留 | 抵達時刻不晚於最後入場時間，沒有最後入場就用閉館時間（Q2） |
| 「X 半天／一天夠嗎」 | 含往返交通；起點用題目提到的住宿或出發地，沒提就用臺北車站（Q3） |
| 只給日期、沒給時刻 | 09:00 出發 |
| 沒給日期 | asked_at 之後最近的平日 |
| 「附近」 | 步行 10 分鐘以內 |
| 「早上」「下午」「晚上」 | 分別是固定時段，在表中明定 |
| 沒說交通方式 | 大眾運輸加步行，不含計程車和自駕 |
| 沒給停留時間 | 用 Q6 停留區間的上下界各模擬一次 |
| 「下週一」「跨年」這類相對時間 | 依 asked_at 換算成絕對日期 |
| 雙胞胎題 | 兩種問法共用同一組預設 |

### 5.5 最容易混淆的幾組邊界

| 這題 | 歸類 | 對照題 | 歸類 | 分界線 |
|---|---|---|---|---|
| 故宮幾點關？ | Q1 | 4 點從臺北車站出發去故宮，來得及嗎？ | Q2 | 需不需要移動 |
| 4 點出發去故宮，來得及嗎？ | Q2 | 4 點出發去故宮，想看一個半小時，來得及嗎？ | Q3 | 有沒有停留 |
| 九份要待多久？ | Q6a | 九份半天夠嗎？ | Q3 | 問一段時長，還是問預算夠不夠（含往返） |
| 先九份再十分，幾點到十分？ | Q3 | 先去九份還是十分？ | Q4 | 順序是已給，還是要求系統決定 |
| 住臺北車站還是西門比較方便？ | Q5 | 先去九份還是十分？ | Q4 | 答案是要選出一個起點或住宿，還是排目的地的先後 |
| 故宮週一有開嗎？ | Q1 | 士林附近週一有開的博物館？ | Q5 | 目標有指名，還是要依條件找 |
| 淡水週六幾點人最少？ | Q6b | 淡水週六幾點日落？ | Q1 | 群體行為，還是地點本身的屬性 |
| 3 點在新竹搭火車，幾點到臺北？ | Q2，答最早抵達 | 3 點那班區間車幾點到臺北？ | Q2，答指定那班車的時刻 | 有沒有指名班次（同類內的預設解讀） |

### 5.6 不收的題（排除清單）

| 題型 | 排除理由 |
|---|---|
| 即時資訊（誤點、即時人潮、即時車位） | 用資料快照無法驗證 |
| 主觀評價與推薦（值不值得、哪家最好吃） | 沒有客觀答案；有可計算條件的部分照 R0 剝除後保留 |
| 天氣、氣候 | 屬於預報或查表，不是時空推理 |
| 票價與票券 | 本質是規則套用；如果 Q6 沒過頻率門檻，列為替補類別（TDX 有臺鐵起訖票價，可以精算） |
| 自駕、停車、機車 | 沒有開放的路況與停車資料 |
| 要系統分配天數的多日行程 | 答案不唯一，已有 TravelPlanner 等 benchmark 在做 |
| 跨地點比人氣（九份和十分哪個人多） | 沒有逐景點的官方計數 |
| 跨意圖的多跳題（照這樣排，哪一站會遇到人潮） | 拆成原子題，或不收 |
| 無障礙、寵物友善等 | 少見 |

### 5.7 「常見」怎麼證明

- **目前的證據**：辯論期間的先導抽查以日本旅遊論壇為主，只能當旁證：
  - C 對 PTT Japan_Travel 標題的抽查：行程請益佔 [問題] 文的 35–78%。
  - 2023 年後 PTT 加背包客棧的補充檢索（數字是下界）：住宿區位 8 篇、人潮 6 篇、周邊查找 5 篇、末班車與機場 3 篇、營業時間 2 篇、行程太趕 2 篇、單獨問停留時長 1 篇。
  - Ram et al. 2021 分析 8,905 則都市大眾運輸提問，歸納出的屬性包含「行程時間」和「服務可用性」。
  - 一篇 2019 年碩論分析 PTT Japan_Travel 7,001 篇文章，結論是交通規劃與行程安排最常被討論。
- **Phase 0（第 1 個月）**：
  - 抽樣：從至少 2 個平台抽出 600 則以上「在範圍內」的原子題。繁中國內旅客和英文來臺旅客分層抽樣、分層報告。
  - 標註：兩人獨立標註，整體 κ 要達 0.8 以上；另外單獨報告最容易混淆的配對：Q1/Q2、Q2/Q3、Q3/Q4、Q4/Q5、Q3/Q6a。
- **門檻**：
  - 保留：佔範圍內原子題 3% 以上、Wilson 95% 下界至少 1.5%、出現在 2 個以上平台。
  - 低於 1%：視為稀有，排除。
  - 1–3%：併入相鄰類別，或列為延伸。
  - 「未覆蓋」佔 5% 以上：新增類別。
- **最可能過不了門檻的是 Q6**：A 認為單獨問停留時長的題少，B、C 認為時段人潮題大多不在捷運沿線，所以把兩者合成一類、設子型。如果合併後仍不到 3%：
  - 停留時間只當 Q3 的參數使用。
  - 時段人潮降為延伸。
  - 改以「票價與票券」替補。

## 6. 系統設計

1. **前端**：
   - 原子化與分類器：6 類，加上「不可答」「需澄清」「範圍外」。
   - EQR/DSL 解析器，做兩個版本：API LLM few-shot；7–8B 開源模型用 LoRA 微調（一般 GPU 就能跑）。
2. **前處理**：
   - 實體連結：中英別名表，對應到觀光署和 OSM 的 ID。
   - 時間正規化：依 asked_at 把相對時間轉成絕對時間，並查辦公日曆。
3. **符號執行器**：
   - OTP2 或 RAPTOR（GTFS 加 OSM 步行）
   - opening_hours 評估器
   - 天文計算（日出日落）
   - PostGIS（等時圈、緩衝區、繞路計算）
   - DuckDB（捷運進出量匯總、停留分布）
   - 行程模擬器
   - 排列窮舉器
4. **回答**：
   - 輸出答案，並附上證據：kb_version、套用了哪些假設、群體統計的 n 和 CI，以及 gold 軌跡。
   - 證據不足時拒答，缺資訊時反問。

## 7. 評估

- **基線**：
  - closed-book LLM（商用與開源）
  - 文本 RAG：把同一份知識庫轉成文字，再加網頁
  - ReAct：直接呼叫原始 API
  - code agent：直接對 GTFS 或 CSV 寫程式（TransitGPT 式）
  - 不用地圖直接生成路線（TransitLM 式），只用於 Q2
  - 論壇最高推文：只用於真實子集
  - oracle-DSL 上界：給正確的 DSL，再交給執行器
- **答案指標**：
  - Bool 和時刻：完全比對（含步行的題有容差）。
  - 班距制路線：看答案是否落在正確區間內。
  - 集合答案：F1 或 valid@k。
  - 序列答案：可不可行、和最佳解差多少、是否在最佳解集合內。
  - Q3 的三值答案：準確率。
  - Q6a：時長區間是否正確。
- **過程指標**：分類 macro-F1、DSL 槽位 F1、實體連結正確率、時間正規化正確率、軌跡有效率（模型給的軌跡能不能通過檢核器）。
- **穩健性**：
  - 改寫一致性：同一題換說法，答案應該不變。
  - 反事實一致性：把日期改成國定假日，答案應該跟著變。
- **拒答與反問**：答對 +1、拒答 0、答錯 −1；另報反問的 F1。
- **真實性落差**：每一類比較雙胞胎題的準確率，用 McNemar 檢定。
- **兩種分數**：
  - 相對知識庫的分數。
  - 抽核後的真實世界分數：抽約 200 個事實，查官網或實地核對。
  - 抽核發現有錯的題另外標記，從主分數中拆開報告。
- **時效漂移**：統計模型用到過時事實的錯誤率，例如臺鐵改點後還在用舊時刻。
- **成本**：token 數和延遲。

|---|---|---|

| 旅遊 QA | [TourismQA](https://arxiv.org/abs/1909.03527) | 做 POI 推薦，沒有時空計算 |
| 方法先例 | [ToolQA](https://arxiv.org/abs/2306.13304)、[KQA Pro](https://arxiv.org/abs/2007.03875)、[SituatedQA](https://arxiv.org/abs/2109.06157) | 沿用「模板＋程式算答案＋改寫」和 as-of 情境化的做法 |

## 9. 時程與關卡

| 月份 | 工作 |
|---|---|
| M1 | Phase 0 頻率校準、資料可行性檢查（§10）、開始徵集題；同時註冊 ODPT，當京都備案 |
| M2–4 | 知識庫、標準答案引擎、預設解讀表 |
| M5–6 | 生成題目、人工驗證、整理真實子集、知識庫抽核 |
| M7–9 | 系統與基線 |
| M10–11 | 實驗與錯誤分析 |
| M12 | 撰寫論文 |

**關卡**：

- **地區**：M1 結束時，論壇來源的範圍內原子題不到 300 題，或任一核心類只出現在 1 個平台 → 改做京都（§11）。
- **營業時間**：能解析並通過驗證的比例低於 50% → 改用 OSM，加上人工整理 200 個 POI。
- **Q6b 時段人潮**：可用的觀光型車站不到 15 個，或真實題中能回答的比例不到 1/3 → 降為延伸。
- **Q6a 停留時長**：抽取 F1 低於 0.9，或樣本數不足 → 降為延伸，Q3 的題目改成一律寫明停留時間。
- **任一類別**：沒過頻率門檻 → 併入相鄰類別或刪除。

## 10. 第一個月待辦

1. 註冊 TDX，實際下載臺鐵、高鐵、臺北公車的 GTFS，確認欄位和會員條款。
2. 下載一個月的 128506 CSV，確認兩件事：時段是不是依出站時間計、實際多久更新一次。再用週末對平日的比例篩出觀光型車站，數一數有沒有 15 個以上。
3. 從觀光署 7777 和 OSM 抽 300 個臺北 POI，測營業時間能解析的比例，目標是 50% 以上。
4. 做 Phase 0：從各平台抽貼文 → 原子化 → 兩人標註 → 算出 κ、各類佔比、出現在幾個平台。同時開始徵集題。
5. 遊記抽取 pilot：找 60 篇臺北和新北的遊記，人工標註造訪地點、順序和停留時間，量測抽取的 F1。
6. 依關卡結果，定案地區和類別。
